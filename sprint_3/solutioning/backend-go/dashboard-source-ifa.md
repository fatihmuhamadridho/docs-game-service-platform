# Go Admin Dashboard Routes — Current Source IFA

> **Document Type:** IFA / API Contract (implementation evidence)  
> **Status:** Current Go behavior; not an approved target design  
> **Service / Domain:** Go Admin Dashboard  
> **Consumer / Partner:** Admin web client

## Design

This IFA documents the 40 registered admin dashboard routes covered by the route matrix below. It is based on `internal/controller/http/admin_game_http.go`, `admin_catalog_http.go`, `admin_member_http.go`, `admin_access_http.go`, `admin_order_http.go`, and `admin_read_http.go`, plus their corresponding controller methods. It records the existing implementation. The individual dashboard IFAs remain proposed business contracts; do not treat their additional fields or rules as implemented unless named here.

- Decision: Existing v1 behavior inventory.
- Previous Endpoint: Same registered routes.

## Business Rules

1. All JSON bodies use the shared decoder: maximum 1 MiB, unknown keys rejected, and a second JSON value rejected.
2. Current response envelope is top-level `{ "code": "...", "message": "...", "data": ... }`; errors serialize `data:null`. This differs from the solutioning target template's nested `status` object.
3. `catalog-manage`, `users-manage`, `settings-manage`, `orders-manage`, `finance-read`, and `dashboard-read` are the permission strings checked by handlers. Activity logs allow either `dashboard-read` or `settings-manage`.
4. Response DTOs and wrapper keys below are the fields explicitly projected by the current controller methods. There is no additional HTTP-level normalization. Fields explicitly marked absent are not emitted by this source; no undocumented property should be inferred from the proposal IFAs.
5. Mutations can write audit context with subject, request ID, source IP, and user-agent. Audit persistence behavior belongs to the corresponding controller/repository.

### Request Validation

1. Category create requires `name` and `slug`; update requires at least one of `name`, `slug`, `description`, or `isActive`. Only those four keys are accepted.
2. Service create requires `gameId`, `categoryId`, `name`, `priceAmount` key, `isCustomPrice`, and `estimateText`; update requires at least one allowed field. Price consistency and field bounds are enforced by `decodeServiceInput` in `admin_catalog_http.go`.
3. Member list accepts only `page`, `pageSize`, `search`, `status`; status is `ACTIVE|BLOCKED`, search max 100, page default 1, pageSize default 20/max 100.
4. Admin account list accepts only `page`, `pageSize`, `search`, `status`, `roleId`; status is `ACTIVE|INACTIVE`, search max 100, page default 1, pageSize default 20/max 100.
5. Order list accepts only `page`, `pageSize`, `search`, `status`; search max 100, status max 40, page default 1, pageSize default 20/max 100. `status` filters localized display labels (`Menunggu Pembayaran`, `Menunggu Validasi`, `Diproses`, `Selesai`, `Dibatalkan`) or special value `Semua Status`; raw status codes do not match.
6. Transaction list accepts only `page`, `pageSize`, `search`, `status`, `method`, `type`; maxima are 100/32/40/24 respectively; page default 1, pageSize default 20/max 100. Filters compare localized DTO values: status labels (`Berhasil`, `Menunggu`, `Gagal`, `Dikembalikan`), method label (`Transfer Bank BCA` for `BCA_TRANSFER`, otherwise stored code), type (`Refund` for REFUND, otherwise `Pembayaran Pesanan`). Unknown filter values are not rejected; they return no matches.
7. Activity list accepts only `page`, `pageSize`, `search`, `category`, `from`, `to`; search max 100, category max 32, dates match `YYYY-MM-DD`, and `from <= to`; page default 1, pageSize default 50/max 100. `category` compares localized labels (`Pesanan`, `Produk`, `Pengguna`, `Konten`, `Pengaturan`); raw category codes do not match. Unknown category values return no rows.
8. Dashboard overview accepts only `from`, `to`, `granularity`; granularity defaults `daily` and is `daily|weekly|monthly`; dates are strict `YYYY-MM-DD`; defaults to UTC today end and six days prior; range max 366 days when both supplied; `from <= to`.
9. Payment review accepts only required orderId/paymentId/decision and optional note; decision is `APPROVE|REJECT`, trimmed note max 500.
10. Settings PUT requires exactly the ten listed fields with source-validated JSON types and bounds above; invalid semantic values map to `SETB02001`/400.
11. Raw path IDs are passed to controller methods; where handler does not parse/validate an ID, precise format acceptance is controller/repository-defined. Do not infer a format beyond source behavior.

### Nested DTO field types

- `Game`: `id/name/slug/serviceSummary/artworkKey` strings (serviceSummary/artworkKey nullable); `serviceCount` integer; `active/popular` booleans; `sortOrder` integer; `updatedAt` timestamp.
- `Category`: `id/name/slug/description` strings; `serviceCount` integer; `active` boolean; `updatedAt` timestamp. Empty stored description projects as empty string.
- `Service`: `id/gameId/game/categoryId/category/name/estimate` strings; `price` number or null; `active` boolean; `updatedAt` timestamp.
- Member list row: `id/name/username/email/status/accountType/tier` strings; `joinedAt` timestamp; `orderCount` integer; `totalSpend` number. Member detail additionally has `whatsapp` string or null.
- Role: `id/name/code/status/description` strings; `adminCount` integer; `permissions` string array; `protected` boolean. Permission catalog rows: `id/code/name/key` strings.
- Admin list row: `id/username/name/email/status/role/lastActive` strings; `roleId` string (empty when no assigned role); `roleIds/roleNames` string arrays; `updatedAt` timestamp. Admin detail: same identity/status fields, `roleIds` string array, `roles` array of `{id,name,code:string; system:boolean}`, `createdAt/updatedAt` timestamps.
- Order list/detail: identifiers, names, labels, statuses, currency and timestamps are strings/timestamps as appropriate; `amount/subtotal/discount` numbers; `expiresAt` timestamp or null. Item `quantity` integer, `unitPrice/lineTotal` number or null; payment `amount` number; proof `fileSizeBytes` integer; all other nested item/payment/proof/history fields are strings or timestamps, with nullable history oldStatus/reason fields serialized null when absent.
- Transaction: IDs and display labels are strings; `amount` number; `createdAt` timestamp; `settledAt` timestamp or empty string. Status history fields `oldStatus/newStatus/reason` string or null and `occurredAt` timestamp.
- Activity: IDs/names/action/target/category/IP/result strings; `occurredAt` timestamp. `adminEmail` may be empty string.
- Settings: names/contact/currency/timezone strings; `siteDescription/businessHours` strings or null; `socialLinks` array of `{label,url}` strings; maintenance/registration flags booleans; `version` integer; `updatedAt` timestamp or null.
- Dashboard: `from/to` timestamps; `granularity` string; metrics counts and change percentages integers, revenue values numbers; series rows `{label:string,orders:int,revenue:number}`; status rows `{status:string,count:int,percent:int}`; popular-game rows `{name:string,count:int,percent:int}`; game-revenue rows `{name:string,amount:number,percent:int}`; payment-method rows `{method:string,count:int,amount:number}`; recent-order rows `{id,user,game,service,status:string,date:timestamp,total:number}`; recent-activity rows `{id,title,detail,category:string,occurredAt:timestamp}`.

HTTP handlers pass the named controller projection through `data`, with route-specific wrappers shown in the matrix below. The tables and verified projection rules in this IFA enumerate all fields emitted by the current controller DTOs; proposal-only fields are not emitted unless listed.

### Controller and repository projection rules

- **Orders** (`internal/controller/admin_order.go`, `internal/infrastructure/mongodb/admin_order_repository.go`): list loads all order, item, and payment records, then filters and pages in memory. Rows sort newest `createdAt` first. Game/service use the first item snapshot or fallback `Game` / `Layanan`; payment method/status come from the newest payment by `CreatedAt`, or method `—` and order-level payment status if none. Status values map to Indonesian labels; unknown values pass through. Detail returns every order item/payment/proof and status history oldest first. Item decimal values parse to `float64` (nil remains null); proof `viewUrl` is `/api/admin/orders/v1/proofs/{proofId}/image`. Repository also loads payment-status histories, but controller discards them (`ph` unused), so no payment-status-history field is emitted.
- **Roles and assignments** (`internal/controller/admin_access.go`, `internal/infrastructure/mongodb/admin_access_repository.go`): list hides soft-deleted roles, ensures seven default permission records exist when absent, and returns permission catalog. Role `permissions` contains the UI keys corresponding to linked permission codes among the seven built-in codes, not raw codes; current role projection does not filter linked permissions by `isActive`. `adminCount` counts non-revoked account-role links regardless of account status. Account list includes only active, non-deleted roles/links, orders rows by Indonesian name, sets `lastActive` to literal `Belum tersedia`, and chooses `role` as `Tanpa Role`, `Admin`, or `Super Admin`; `roleId` prioritizes Super Admin then first assigned role. Account detail `roles[]` contains active, non-deleted assigned roles only. Role creation inserts the role before resolving permission IDs; an unavailable permission can return 400 after role insertion. Role update writes scalar fields before resolving/replacing selected permissions; permission failure can therefore follow a successful scalar update. Role permission replacement and account role replacement/revocation execute multiple writes without a transaction and can partially apply on repository error. Role/account deletion is soft-delete/revoke behavior.
- **Transactions** (`internal/controller/admin_read.go`): repository reads all transaction records; controller filters by exact status/method/type and case-folded substring across transaction number, order ID, customer name/contact, and provider reference, sorts newest first, then paginates. Status labels: SUCCESS/SETTLED/COMPLETED→`Berhasil`, PENDING/PROCESSING→`Menunggu`, FAILED/CANCELLED→`Gagal`, REFUNDED→`Dikembalikan`; unknown status passes through. Type REFUND→`Refund`, all others→`Pembayaran Pesanan`; BCA_TRANSFER→`Transfer Bank BCA`. Missing customer name defaults `Pelanggan`, missing contact/reference defaults empty string, missing settledAt defaults empty string. Summary is computed after filters but before paging; successful amount sums only `Berhasil`, and pending/refunded counts use those labels. Detail adds all transaction status-history events sorted oldest first.
- **Activity logs** (`internal/controller/admin_read.go`): repository reads all rows; controller filters category/date/search, sorts newest first, then paginates. Category labels ORDER/CATALOG/USER/CONTENT→`Pesanan`/`Produk`/`Pengguna`/`Konten`; every other category maps to `Pengaturan`. Missing actor name→`System`, email→empty, target reference→target type, source IP→`—`; only result exactly `SUCCESS` maps to `Berhasil`, all other values map to `Gagal`. Summary counts selected rows before pagination. Date end is inclusive through 23:59:59.999 UTC.
- **Settings read/write** (`internal/controller/admin_read.go`, `internal/infrastructure/mongodb/admin_read_repository.go`): singleton key `current`; missing row reads defaults `siteName=JokiHub`, empty description, empty `socialLinks`, `defaultCurrency=IDR`, `timezone=Asia/Jakarta`, `allowRegistration=true`, other booleans false/strings empty, `version=0`, `updatedAt=null`. Persisted nil description reads as empty string. `socialLinks` decoder accepts Mongo `bson.A` entries represented as `bson.M` or `bson.D`, keeps entries where label or URL nonempty; if resulting list is empty and legacy `instagram_url` exists, synthesizes `{label:"Instagram",url:...}`. Update trims siteName/description/email/WhatsApp/businessHours/links, lowercases email, derives legacy instagram_url from case-insensitive Instagram label, increments version (new record version 1), stamps UTC updatedAt, and upserts. It then attempts activity insert but ignores activity-write error, and rereads saved settings for response. Settings validation maps to `SETB02001`/400; repository errors map to `SETT03001`/500.
- **Dashboard overview** (`internal/controller/admin_read.go`): repository returns all orders, transactions, users, services, order items, and activity rows; calculations happen in memory. Period is inclusive `from`/`to`; comparison period has same duration immediately before `from`. Order count includes every order state; revenue includes PAYMENT transactions whose statuses are SUCCESS/SETTLED/COMPLETED. Percent change rounds to nearest integer and returns zero when prior value is zero. User count counts non-deleted accounts regardless of status; service count counts active, non-deleted services. Series buckets are created for dates containing orders or qualifying transactions; weekly buckets begin Sunday and monthly buckets use day one. Game counts use each order's first item game snapshot, falling back to `Game`; game revenue is attributed to qualifying payment transaction via order ID. Popular games and game revenue return top five; percentages are relative to maximum value (minimum denominator 1), not totals. Payment method BCA_TRANSFER is labeled `Transfer Bank`; other method codes pass through. `recentOrders` and `recentActivity` are the five newest records globally, not restricted to selected period. Empty collections produce empty arrays and zero metrics.
- **Read errors**: repository errors from transactions map to `TRNT03001`, activity to `ACTT03001`, settings to `SETT03001`, dashboard to `DSHT03001`, all HTTP 500 with fixed Indonesian fallback message. Typed validation/not-found errors retain their explicit status/code. Exact underlying database failure cause is not serialized.
- **Admin order mutations** (`internal/infrastructure/mongodb/admin_order_repository.go`): payment review accepts only a payment in `PENDING_REVIEW`; APPROVE sets payment `PAID` and order `PROCESSING`, creates a SUCCESS financial transaction and transaction-history row. REJECT sets payment/order to `UNPAID`/`PENDING_PAYMENT` when expiry remains in future (clears submittedAt), otherwise `FAILED`/`CANCELLED`. Both update payment/order histories, using optional note as reason. Conditional update miss maps `ORDB02004`/409; non-reviewable state also maps `ORDB02004`/409. Multi-write failure attempts compensating deletes/restores; compensation errors are ignored. Completion is permitted only for `PROCESSING`+`PAID`, then sets `COMPLETED` and appends order history; conditional update miss maps `ORDB02004`/409, non-completable state same code/status. Repository/database errors fall back to `ORDT03001`/500.
- **Admin catalog joins** (`internal/controller/admin_catalog.go`, `internal/infrastructure/mongodb/catalog_repository.go`): category rows exclude soft-deleted entries; `serviceCount` counts services with matching category and `deleted_at:null` (including inactive services). Service list excludes deleted services and joins game/category names from all records; an unresolved referenced ID yields empty name, while a soft-deleted but still present game/category retains its name. Service options include non-deleted games/categories regardless of active flag. Fixed-price service serializes numeric `price`; custom-price service serializes null. A service may reference inactive game/category only when service itself is inactive; active service requires active, non-deleted game and category. Category delete rejects while any linked service exists, including soft-deleted services, because delete count intentionally omits the `deleted_at` filter; it exposes exact `linkedServiceCount`. These are controller business errors (`SCAB02001/2/3/4`, `SRVB02001/2/3`); repository failures become `SCT03001` or `SRVT03001` HTTP 500. Repository does not emit separate domain errors for storage failures.
- **Games and member aggregates** (`admin_game.go`, `admin_member.go`, `admin_member_repository.go`, `catalog_repository.go`): admin game list excludes soft-deleted games, sorts ascending `sort_order`, and `serviceCount` counts only active, non-deleted services. Member list reads non-deleted records from `user_account`, optionally filters exact status/search, sorts joinedAt descending (fallback createdAt; ties ObjectID descending), then pages. Current DTO sets `accountType` to literal `MEMBER`; tier comes from member profile or defaults `BRONZE`; `orderCount` counts all linked orders and `totalSpend` sums `TotalAmount` for `PaymentStatus == PAID` only. Detail applies same profile/tier/order/spend rules and returns nullable `whatsapp`. Counts and sums vary with persisted MongoDB records; query predicates and defaults above are fixed by source. `admin_read_test.go` verifies stable source encounter order for equal dashboard status/game/payment-method sort keys.
- **Member update/delete side effects** (`admin_member.go`, `admin_member_repository.go`): update writes account patch first; if status changed it then inserts status history. History insert failure returns technical error after account update has already succeeded (no rollback). Delete sets `deleted_at` and status `BLOCKED`; response is `{deleted:true}`. Create validates uniqueness then returns `USRT02001`/503 without persisting an invite or sending mail.
- **Role assignment errors and mutations** (`internal/controller/admin_access.go`, `internal/infrastructure/mongodb/admin_access_repository.go`): malformed/missing role IDs map `ROLB02001`/400; missing role `ROLB02002`/404; duplicate role name/code `ROLB02003`/409; missing/inactive permission selection `ROLB02003`/400; system-role mutation/deletion `ROLB02004`/409; assigned-role deletion `ROLB02005`/409. Admin role IDs must reference active, non-deleted roles; unavailable role is `USRB02003`/400. Role permission replacement deletes prior links then inserts selected links; account role replacement reactivates matching revoked links, revokes removed links, and inserts new links. These sequences are not transactional; storage errors map to `ROLT03001`/`USRT03001` HTTP 500.

These projections are source-resolved. The remaining unknowns are target decisions captured in `../dashboard/QUESTION.md`; they are not unknown Go fields.
