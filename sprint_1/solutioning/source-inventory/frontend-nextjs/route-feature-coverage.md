## Purpose and audit method

This document maps every current App Router page to its feature page component and the closest solutioning documentation in the owning proposed sprint. Route files are composition wrappers; UI behavior is owned by the imported `src/features/<Feature>/views/pages/*` component. API behavior below is included only where supported by existing solutioning documents. A missing API document means this audit did not find an authoritative contract for that route; it does not prove that no API call exists.

`nextjs-game-service-platform/AGENTS.md` and `DESIGN.md` describe a broader product intent than the currently documented API set. The design document specifically marks auth, tracking, payment-provider, and admin screens as future wireframe scope; runtime routes now exist for many of those areas.

## Known interaction, state, validation, and error behavior

### Checkout and payment

- `/order` reads optional `searchParams.game` and supplies it to `CheckoutPage` (`src/app/order/page.tsx`). `/order/[gameSlug]` supplies the slug to `OrderPaymentPage` (`src/app/order/[gameSlug]/page.tsx`).
- Checkout implementation documentation specifies `POST /api/orders/v1/checkout`, `Idempotency-Key`, active game/service checks, server-side price reload, quantity and account/contact data, and `QRIS` or `BCA_TRANSFER`. Custom-price services remain quote-only.
- Payment instructions are configuration-dependent. Missing instructions/storage configuration should return explicit `503`; the UI must not claim payment success before admin approval. Proof upload accepts supported image formats up to 5 MiB; payment status is polled and replacement proof is possible after rejection while order remains valid.
- Detailed UI field schemas and exact client validation/error copy are not established by route wrappers or the cited solutioning note; treat as unknown until the feature page/forms are inspected.

### Tracking

- `/cek-pesanan` uses order number plus WhatsApp lookup; successful lookup returns safe order snapshot/timeline and tab-scoped tracking token.
- Detail page refresh is documented at 30-second intervals. Expired token returns user to lookup; transient service failure preserves last confirmed status. Do not expose full phone, internal actor IDs, credentials, or review notes.
- Route segment is named `[orderId]`, while API/documentation uses order number. Confirm whether it carries an order number or internal ID before changing URL/API behavior.

### Authentication and access control

- `/login` is shared between customer/admin and accepts username or email. Admin success routes to `/admin`; customer success routes to storefront. Customer/admin sessions and refresh cookies are isolated.
- `/register` is gated by `FEATURE_REGISTER`; recovery routes are gated by `FEATURE_PASSWORD_RECOVERY`. Disabled routes call `notFound()` in route source.
- `/admin/*` requires an admin session; role permissions are represented in admin token and API handlers. `/403` is the permission-denied destination/presentation.
- Exact client-side validation feedback and component-level loading/error states were not captured by route wrappers; backend constraints are in `solutioning/auth-user-handling.md`.

### Admin list and management screens

- Routes under `/admin` compose dedicated feature pages. Existing dashboard API documents establish several list/detail/CRUD contracts, but they do not document table columns, search/filter UI, pagination control state, modal behavior, empty/loading states, or mutation confirmation/error feedback.
- No matching solutioning contracts were found for announcements, bank accounts CRUD, banners, complaints, FAQs, manual top-ups, CMS pages, payouts, or refunds. Those features are represented by page components, but their API/state/validation behavior remains unknown in this audit.
